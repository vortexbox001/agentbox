# Research: Agent Management UI

**Phase 0 output** — every open technical question from the plan's Technical Context, resolved.

## R1. Frontend architecture

**Decision**: Server-rendered Jinja2 pages (already a dependency of the `ui` image) plus two hand-written ES modules (`shell.js`, `agent-form.js`) that talk to a JSON API. No bundler, no framework, no Node toolchain.

**Rationale**: The spec asks for a barebones skeleton to build on, the host may be a Raspberry Pi, and the repo has no JavaScript toolchain. The dynamic behaviour (harness-dependent fields, model filtering, secret flags, on-demand YAML preview, unsaved-changes guard) is well within reach of a schema-driven vanilla module, and keeping the schema server-side means the browser never re-implements validation — it renders what `/api/schema` describes and the server is the authority.

**Alternatives considered**:
- *React/Vite SPA* — matches the prototype's flavour but adds a build step, Node in CI, and a second place where the field schema would have to live. Rejected for scope.
- *HTMX partials* — attractive for list/detail, but the form's per-keystroke behaviours (secret flagging, live preview) push toward client-side state anyway. Rejected as a half-measure.

## R2. Serving the design system at `/design-system`

**Decision**: `git mv "ui/Archon Agent Orchestration Platform" ui/design-system` (contents unchanged) and mount it with `StaticFiles` at `/design-system/`. `GET /design-system` (no slash) responds `302 → /design-system/`, and `GET /design-system/` serves `Archon Design System.dc.html`. The app's own pages link to `/design-system/archon-tokens.css` so there is exactly one token file.

**Rationale**: `support.js` bootstraps itself — it injects React 18.3.1, ReactDOM, and Babel standalone from unpkg and then boots the `<x-dc>` root — and the Design System document contains zero `{{ }}` bindings or `<sc-if>` blocks, so it renders as-is with no server-side transformation. The trailing slash matters: the document references `./support.js` and `./archon-tokens.css` relatively, and a browser resolves those against the document URL, so serving it at `/design-system` (no slash) would request `/support.js` and break the page; at `/design-system/` they resolve to `/design-system/support.js` and `/design-system/archon-tokens.css` inside the mount. A test asserts both assets return 200 and the served page's relative references are reachable. The Prototype and Agent Orchestration documents are also reachable under `/design-system/` for reference. The page is not linked from the shell's navigation (FR-014).

**Alternatives considered**:
- *Copy the tokens into `ui/static/`* — creates drift between the library and the app. Rejected.
- *Convert the .dc.html to plain HTML* — unnecessary since it renders standalone; would also fork the reference. Rejected.

**Caveat**: `/design-system` needs internet access (unpkg + Google Fonts). The main app degrades gracefully without fonts (system fallbacks in the token file).

## R3. Writing YAML with explanatory comments

**Decision**: A small schema-driven emitter in `agents_store.py`: iterate the schema's sections and fields in canonical order, skip fields not applicable to the harness or left at "unset", serialise each scalar with `yaml.safe_dump(value, default_flow_style=True).strip()` for correct quoting, and append `  # <explanation>` from the schema. Lists (`allowed_tools`, `disallowed_tools`) emit as block sequences with the comment on the key line; maps (`env`) emit one `KEY: value` per line. A header comment names the harness and states that the file is generated by the agentbox UI.

**Rationale**: Clarification Q2 chose "regenerate with the UI's standard explanations", which removes any need to preserve arbitrary hand-written comments — the emitter only ever writes what the schema knows. PyYAML handles quoting edge cases (`${GITHUB_TOKEN}`, cron strings, `[1m]` suffixes, empty strings) and is already installed. Reading stays `yaml.safe_load`.

**Alternatives considered**:
- *ruamel.yaml round-trip* — preserves comments, but that is explicitly not wanted; its comment-writing API is awkward and it adds a dependency. Rejected.
- *Jinja2 text template for the file* — workable, but quoting rules would be re-implemented by hand. Rejected.

## R4. Harness × model compatibility and choice sources

**Decision**: `schema.py` holds a harness matrix; the LiteLLM alias list is read from `litellm/config.yaml` (`model_list[].model_name`) at request time, falling back to the hardcoded `[cheap, smart, opus, kimi, kimi-k3]` if the file is missing.

| Harness | Model input | Accepted values | Effort choices |
|---|---|---|---|
| `claude-code` | select + "custom id" text | aliases `sonnet`, `opus`, `haiku`, `fable`; or full id matching `^claude-[a-z0-9.-]+(\[1m\])?$`; blank = CLI default | `low`, `medium`, `high`, `xhigh`, `max` |
| `pi` | select + "provider/model" text | LiteLLM aliases; or a string containing `/` (passed through) | `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` |
| `api` | select only | LiteLLM aliases | — (no effort) |
| `codex` | text with suggestions | any non-empty string, blank = codex default; suggestions `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.3-codex-spark` | `none`, `minimal`, `low`, `medium`, `high`, `xhigh` |

Field applicability per harness is in [data-model.md](data-model.md). Rules are taken from `orchestrator/factory.py` and the README's YAML reference, which are the authoritative behaviour.

**Rationale**: FR-006/FR-007 and FR-003a require filtered choices where the valid set is known and free text only where it is open-ended. Reading the LiteLLM config keeps the UI honest with reality (Constitution VI) when aliases are added.

**Alternatives considered**: hardcoding aliases only (drifts), or querying LiteLLM's `/models` at runtime (needs the master key in the UI container — violates "no secrets in the UI"). Rejected.

## R5. Dagster reload

**Decision**: `POST /api/dagster/reload` sends `mutation { reloadWorkspace { __typename ... on PythonError { message } ... on UnauthorizedError { message } } }` to `${DAGSTER_URL}/graphql` with a 10 s timeout and maps the result to `{ok: bool, message: str}`. Save/delete endpoints accept `reload_dagster: true|false` (default true) and include the reload outcome in their response; the file operation succeeds independently of the reload outcome.

**Rationale**: This is the mutation the current control panel already uses; the addition is inspecting the union type so failures are reported instead of swallowed (edge case in spec). Keeping reload as a flag on the write call gives the one-click flow the clarification asked for while allowing opt-out.

**Alternatives considered**: `reloadRepositoryLocation(repositoryLocationName)` — more targeted but requires knowing the location name from `workspace.yaml`; `reloadWorkspace` is sufficient for one location. Rejected for now.

## R6. Cron validation

**Decision**: `croniter.is_valid(expr)` server-side; an empty string means manual-only. The browser does a light 5-field shape check for instant feedback and defers to the server's verdict.

**Rationale**: Dagster's own schedule parsing accepts standard 5-field cron; `croniter` is small and pure Python. Hand-rolled regexes miss ranges/steps/names.

## R7. Secret-like detection heuristic

**Decision** (`secrets.py`, mirrored in `agent-form.js`): a plain (non-`${NAME}`) env entry is flagged when either
- the **name** matches `(TOKEN|SECRET|PASSWORD|PASSWD|API_?KEY|PRIVATE_KEY|CREDENTIAL|AUTH)` case-insensitively, or
- the **value** matches a known prefix (`sk-`, `sk-ant-`, `ghp_`, `github_pat_`, `gho_`, `xox[abp]-`, `AKIA`, `AIza`, `-----BEGIN`) or is ≥ 20 characters with no whitespace and at least three of {lower, upper, digit, symbol}.

`${NAME}` references are never flagged. The server returns HTTP 409 `{"flagged": ["KEY", ...]}` unless the request carries `confirm_not_secret` listing every flagged key; the form shows the inline warning immediately and turns the 409 into the confirmation dialog.

**Rationale**: Clarification Q4. Name-based rules catch the common case (`GITHUB_TOKEN: ghp_…`); value-based rules catch mis-named ones. False positives are cheap (one confirmation), false negatives are the expensive case, so the heuristic leans strict.

## R8. Agent identity, renaming, and templates

**Decision**:
- `name` is validated as `^[a-z0-9]+(-[a-z0-9]+)*$` and is the filename (`agents/<name>.yaml`). On create, an existing file → HTTP 409.
- `name` is **read-only on the edit page**; renaming is delete + create (documented in the UI help text).
- Files starting with `_` are hidden from the list but offered on the New Agent page as "Start from template" (pre-fills the form from the template's values with `name`/`enabled` cleared). This replaces README step 1 ("copy a template").

**Rationale**: Rename-on-edit would need a two-file transaction and Dagster job renaming semantics the spec doesn't ask for. Template pre-fill is cheap and preserves the templates' role.

## R9. Invalid YAML files

**Decision**: The list shows such files with an error badge and the parse message. Opening one loads the form with defaults, shows the error banner, and displays the raw file contents in a read-only block so the operator can retype values; saving regenerates the file.

**Rationale**: The form is the only editing surface (Q5), so "open and fix" means "re-enter"; exposing the raw text keeps that practical.

## R10. Prompts directory and file ownership

**Decision**:
- Compose `ui` service gains `./prompts:/opt/agentbox/prompts` (rw) and `./litellm/config.yaml:/opt/agentbox/litellm/config.yaml:ro`, and runs as `user: "${AGENTBOX_UID:-1000}:${AGENTBOX_GID:-1000}"` (documented in `.env.example`).
- New prompt filenames are validated as `^[a-z0-9][a-z0-9._-]*\.md$` (auto-appending `.md`); an existing file → 409. Prompt content is required to be non-empty.

**Rationale**: Today only `agents/` is mounted, so the prompt library cannot be served or written. Running as the host uid avoids root-owned files appearing in the git checkout.

## R11. Testing approach

**Decision**: `pytest` with a `conftest.py` that points `AGENTS_DIR`, `PROMPTS_DIR`, and `LITELLM_CONFIG` at `tmp_path` copies and creates a `TestClient`. `dagster.reload` is monkeypatched in API tests. Coverage targets: schema matrix, emitter output (golden file for one agent per harness), store CRUD and guards, secret heuristic table, every endpoint's success and error paths. Browser-only behaviours are covered by the quickstart checklist.

**Rationale**: No test infrastructure exists yet; the module boundaries above make the server fully testable without Docker or Dagster.

## R12. Schema evolution (the file-based analogue of database migrations)

**Decision**: There is no database in this feature, so there is nothing for Alembic to manage; the agent "data model" is `agents/*.yaml` plus `ui/schema.py`. The same problem Alembic solves — files written under an older schema still exist when the schema changes — is handled with three mechanisms:

1. **Schema version stamp**: the emitter writes `# agentbox-schema: <N>` in the file header. Files without the stamp (hand-written, or written by the orchestrator's templates) are treated as version 0.
2. **Ordered migrations on load**: `schema.py` keeps `MIGRATIONS: list[tuple[int, Callable[[dict], dict]]]` — one pure function per version bump (rename a key, split a field, change a default's meaning). `agents_store.read()` applies every migration above the file's stamped version before the dict reaches the form; the file on disk is only rewritten when the user saves. A test loads every real `agents/*.yaml` through the chain and asserts the result validates.
3. **Unmanaged keys are preserved**: any key the schema does not know (e.g., the orchestrator gains a field before the UI does) is carried through untouched and emitted in a final `# --- Unmanaged (not edited by the UI) ---` section, so a UI save never silently drops configuration.

**Rationale**: The user's stated preference is Alembic-style migrations. This gives the equivalent discipline for file-backed config — versioned, ordered, forward-only, tested against real data — without inventing a database for a feature that has none. It also keeps the orchestrator as the authority on what keys mean (Constitution II, VI): the UI never blocks a key it does not understand.

**Forward plan**: the features already flagged as "later" (recent runs, performance, tools) need queryable history. When the first of them lands, introduce SQLAlchemy models + Alembic in `ui/` (`ui/alembic/` with `alembic.ini`, migrations run at container start) for that state. Agent definitions stay in YAML — they are the declarative interface the orchestrator reads and belong in git, not in a database.

**Alternatives considered**: a `schema_version` key inside the YAML body (would leak into the orchestrator's config surface; a comment is invisible to `safe_load`); dropping unknown keys (data loss when the orchestrator moves first); running migrations as a one-off CLI (users would have to remember it — applying on load is self-healing).

## R13. App shell derivation from the prototype

**Decision**: Reproduce the prototype's shell (220 px sidebar, 56 px top bar, scrollable 28 px-padded content) as `base.html` + `app.css` using the `--ax-*` tokens, with the brand block reading "agentbox" (lower case, brand gradient mark), a single "Agents" nav item, and a Dagster status block in the sidebar that links to `DAGSTER_URL`. Top bar shows page title + breadcrumb slot; the notification bell and avatar from the prototype are omitted (nothing behind them yet).

**Rationale**: Matches the spec's LHN/TLN/MWP framing and the design system's App Shell layout pattern; omits chrome that would be non-functional placeholders.
